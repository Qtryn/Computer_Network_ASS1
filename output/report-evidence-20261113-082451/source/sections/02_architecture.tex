\section{System Architecture}
\subsection{Components and communication paths}

\Cref{fig:architecture} shows the browser--client--server structure. Each browser talks only to its \emph{own} Python client through a loopback HTTP/HTTPS listener. The client uses TCP for control and UDP for application data; the server validates the session and relays messages to the intended online recipients. It does not serve as a persistent chat history or file store.

\subsection{Login and session lifecycle}

A client starts with \texttt{HELLO}/\texttt{HELLO\_OK}, then sends \texttt{LOGIN}; on success, the server returns \texttt{LOGIN\_OK} with a session token, online users, and UDP port. In account mode, \texttt{REGISTER} and \texttt{LOGIN} use verified TLS, while the local browser connection uses HTTPS. Accounts are kept as salted PBKDF2-HMAC-SHA256 hashes in an atomically updated JSON file, not plaintext passwords. The server maintains one active login per username and tracks each user's IP address and UDP port.

Clients send periodic TCP \texttt{PING} controls; logout, expiration or disconnection closes the session and updates the online list. The local browser listener remains available for a fresh login. The simple state transitions are shown in \cref{fig:session-state}.
